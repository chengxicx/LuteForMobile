一、根因

服务端 Song（lute-v3）有一套「Book Set」机制：某个 tag 被配置成 Book Set 后， 它下面的书**不再逐本返回**，而是聚合成一行。 

-- lute/book/datatables.py  _series_union_base_sql()  series_branch
SELECT
    NULL AS BkID,              -- ← 聚合行没有自己的书 id
    agg.lgid AS LgID,
    L.LgName AS LgName,
    agg.tagtext AS BkTitle,    -- ← 标题就是 tag 名
    1 AS PageNum,
    agg.bookcount AS PageCount,-- ← PageCount 是「书数」，不是页数
    ...
    'series' AS BookType,      -- ← 唯一的判别标志
    agg.tagtext AS SeriesTag,
    agg.bookcount AS SeriesBookCount,
    agg.readcount AS SeriesReadCount,
    agg.statspending AS SeriesStatsPending

客户端此前完全不知道 BookType='series' 的存在（全项目 grep series 只有一句无关注释），于是这条链路断了：

1
服务端返回聚合行，BkID = NULL
2
客户端 Book.fromJson 的容错转换把 NULL 变成 0
3
被当成一本 id=0 的普通书，卡片显示 「1/12」这种页数式进度（其实 1 是常量、12 是书数）
4
点击 → 请求 /book/edit/0 → 服务端 ValueError: No book with id 0 found → 阅读器空白
5
上一轮为「幽灵书」加的 id > 0 过滤，恰好把聚合行一并丢掉 —— 书架不再报错，但 212 本书连同 8 个入口一起消失了
教训：容错转换不能把「无效」静默变成「合法值」，尤其不能用于主键。 它把「整页崩溃」变成了「单本书静默损坏」，反而更难排查。正确做法是让业务语义 （isSeries）参与判断，而不是只看 id 的数字。

二、服务端契约（不需要改服务端）

关键发现：服务端的聚合开关是「搜索词或 tag 过滤非空就关闭」，并且已经暴露了 filtTag 表单字段。这意味着客户端**不需要新增任何服务端接口** 就能拿到聚合行背后的成员书。 

# lute/book/datatables.py
use_series_aggregation = (
    len(series_tags) > 0 and not search_value.strip() and not tag_filter
)
客户端请求服务端行为用途
POST /book/datatables/active
（无 filtTag / 无搜索词）		 返回 8 个聚合行 + 57 本扁平书 书架列表
POST /book/datatables/active
+ filtTag=ai-story		 关闭聚合，返回该 tag 下 12 本扁平书 Book Set 详情页
POST /book/datatables/active
+ search[value]=xxx		 关闭聚合，返回匹配的扁平书 搜索（服务端既有行为，客户端未改）

为什么成员书要单独请求

聚合态下服务端只回聚合行，成员书**根本不在响应里**。所以详情页必须再发一次带 filtTag 的请求。这比在客户端拿全量书单自己按 tag 过滤更省流量， 也和网页版 /book/series/<tag> 的语义一致。

五、未验证 / 已知取舍

  • 真机 UI 已通过截图逐屏核对（书架 + 详情页），但未覆盖：横竖屏切换、 超大字号无障碍设置、已归档 Book Set 视图、12 本成员书逐个点开。
  • 统计补算是一次性后台任务。每个 Book Set 每个会话只补算一次 （用 _seriesStatsWarmedSeries 去重），避免服务端始终算不出统计时 陷入「补算 → 重载 → 再补算」的死循环。代价是若首次补算失败，本次会话不会再重试。
  • 详情页只显示本语言的成员。服务端对同一个 tag 会按语言各出一行聚合行， 详情页因此按行语言收敛列表，保证「卡片上的 N」与「列表条数」一致。 当前 8 个 Book Set 都是单语言，这条规则暂不产生可见影响。
  • 已归档成员书未在详情页展示。聚合行只统计未归档书；归档成员需要走 filtTag + archived 接口，本轮未接。
  • 搜索态会展开聚合。这是服务端既有行为（搜到就能找到），客户端未做干预 —— 搜索结果里同一个 tag 的书会逐本出现，聚合卡片同时消失。

六、收尾：两条导航链路的修正

上表第 9 项把 navigateToReader 改成可以显式接收 Book，但当时漏掉了「长按成员书 → 详情弹窗 → Start Reading」 这条路径：弹窗里的按钮还在调 navigateToReader(book.id)， 并且只 pop() 一层。

两个独立缺陷，静态分析都发现不了：
  1. 丢标题和语言。成员书被聚合行隐藏，不在书架列表里， _handleNavigateToReader 的兜底分支找不到它， 于是阅读器顶部没有书名、currentBookLangId 保持旧值。
  2. 阅读器被盖住。弹窗压在 Book Set 详情页之上，只 pop 掉弹窗的话， 阅读器切换发生在下面那一层，用户看到的还是 Book Set 列表 —— 表现就是「点了 Start Reading 没反应」。
文件修正
books/widgets/book_details_dialog.dart Start Reading 改为 navigateToReader(book.id, null, book)； 关闭方式从 pop() 改为 popUntil((route) => route.isFirst)， 把可能压着的详情页一并弹掉，回到主界面后阅读器才可见
books/widgets/series_detail_screen.dart 成员书入口的 _openBook 由「先 pop 再导航」改为先导航再 pop： 原顺序会先露出主界面原来的标签页（书架），下一帧才切到阅读器，闪一下
