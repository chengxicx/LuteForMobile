朗读失败：Empty audio returned from Edge TTS server

客户端 LuteForMobile  ·  服务端 lute-v3  ·  2026-09-23

阅读器顶部一直挂着一条红色错误横幅，点进去看是 Empty audio returned from Edge TTS server。 它不是网络问题，也不是偶发抖动 —— 在默认设置下，任何日文书的朗读都必然失败， 而且失败一次之后会被永久缓存。下面是完整链路。

一、根因链路

1
客户端把 Edge TTS 的语言写死在设置里：TTSProvider.edgeTTS: TTSSettingsConfig(languageCode: 'en')。 于是朗读请求永远是 /tts/en/<text>，与正在读的书无关。
2
服务端 voice_for_tag("en") 选中 en-US-AvaNeural（英文语音）， 却拿到了日文文本。edge-tts 对语种不匹配的输入抛 NoAudioReceived。
3
communicate.save(filepath) 是先创建目标文件、再联网合成。 抛异常时文件已经建好了 —— 于是磁盘上留下一个 0 字节的 mp3。
4
路由的缓存判断只看 os.path.exists(filepath)， 0 字节文件被当成缓存命中，直接 send_file 出去： HTTP 200 + 空响应体，还带着 Cache-Control: immutable, max-age=31536000。
5
客户端拿到 200，但 bytes.isEmpty 成立 → 抛 TTSException('Empty audio returned from Edge TTS server')。 因为第 4 步永久缓存，这个失败再也无法自愈。
核心问题不是「选错了语音」，而是「失败被当成了成功并永久保存」。 第 3、4 步让任何一次瞬时失败都会变成长久故障 —— 这才是这条错误横幅一直消不掉的原因。

第 4 处：修好「跟随书的语言」之后，真机上照样失败

把第 1 步改成「朗读语言跟随当前书」之后，装到真机上点播放， 错误横幅原封不动。抓服务端日志看到的请求依然是： 

GET /tts/en/%E3%80%90%E4%B8%80%E3%80%91  200  0 字节

原因是：「当前书的语言」这个 provider 在最常见的场景下根本是空的。

打开书的方式是否写入 currentBookProvider朗读语言
从书架点一本书
_handleNavigateToReader()		 是 调用 setBook() 正确（ja-JP）
启动 App 时恢复上次在读的书
_loadLastReadBook()		 否 只调 loadBook(bookId) 退回 en

恢复路径绕过正常入口，currentBookProvider 一直是空的， 于是 _resolveEdgeLanguageCode() 里的 languageName 为 null，只能落到设置页的兜底值 'en' —— 绕了一圈还是英文语音。

一个容易踩的细节： Book.language 来自 json['LgName'] ?? ''， 缺失时是空串而不是 null。而判断用的是 languageName.trim().isNotEmpty， 空串会静默滑到兜底值，不会报错、也不会有任何日志。

由此也可以确定：只修客户端并不能根治。任何一次合成失败（网络抖动、 edge-tts 接口变更、生僻文本）都会再造一个永久的 0 字节缓存，因此 服务端「0 字节不算缓存命中 + 先写 .part 再原子 rename」这两处必须一起部署。

第 5 处：服务端 502 后变成了更丑的 UI 错误

部署服务端补丁后，」 那句不再留下毒缓存，但是变成另一种更难看的故障：服务端返回 502 + JSON，客户端把它当成"服务器挂了"， 把整段 DioException 文案（连 Mozilla 文档链接都打出来）甩到 UI 上 —— 比之前的 "Empty audio"横幅更糟。

根因：阅读器走的是 EdgeTTSService.getAudioBytes() 路径， 而我上一轮只改了 speak()。同一个服务端类有两个公开方法， speak() 和 getAudioBytes()，都会调用 _fetchAudio()。

修法：把「该片段无法合成」抽成一个专用类型 TTSUnpronounceableFragmentException extends TTSException， _fetchAudio() 检测到 502 + marker 时抛它。 getAudioBytes() 直接透传，上游 sentence_tts_provider.speakSentence 捕获后静默重置 state； speak() 则让异常向外传播（它本身就是 TTSException，会被末尾的 catch (e) { if (e is TTSException) rethrow; } 原样抛出）， 由调用方 tts_player_provider._speakCurrent 用 on TTSUnpronounceableFragmentException { _onServiceCompleted(); } 直接当成「这一句播完、跳下一句」处理。

为什么不再用 speak() 里补 PlayerState.completed 的老做法：那是把合成事件塞进 service 的 broadcast stream，若调用方在「emit」与「delivery」之间重新订阅（如 _onServiceCompleted 里又调 _speakCurrent → _subscribeService 取消旧订阅），该事件会被丢掉，朗读就卡在不可发音的那句。 改成调用方直接捕获异常来推进，不依赖任何 stream 事件，最稳。

教训：同一个服务的「失败处理」逻辑要在 所有公开方法上保持一致；且「推进到下句」这种控制流应由阅读器自己掌握， 不要靠往音频播放器的状态流里注入假事件。

六、补充定案（第二轮）：真正的拦路虎是 Cloudflare

上一轮把失败信号定为「502 + {"error":"tts synthesis failed"}」， 客户端靠匹配这个 JSON 标记来识别「这句念不出来」。这个约定在公网侧从来没有生效过 —— 因为生产站走 Cloudflare，而 CF 会把源站 5xx 的响应体整个替换掉。

路径状态体积Content-Type响应体
直连源站（:80 + Host 头） 50233 Bapplication/json {"error":"tts synthesis failed"}
经 Cloudflare 50216 Btext/plain error code: 502  （Server: cloudflare）
  • 后果：_fetchAudio 里 text.contains('"tts synthesis failed"') 恒为 false ⇒ 抛通用 TTSException('Edge TTS request failed: …') ⇒ 播放条置 error，弹出红色横幅（内容是 Dio 的原始异常文本）， 朗读停在《横浜のアパートの惨劇》第 7/33 句（被切成只剩一个 」 的碎片）不再前进。 用项目自带 dio 在生产机上复现，客户端视角确为 status=502 / containsMarker=false / server=cloudflare。
  • 订正上文的结论：第五节「红色错误横幅已消失」不成立，横幅一直都在， 只是它位于播放条顶部，截图区域偏低就会看不见。 同理，当时猜的「APK 滞后」与「另一条路径不补发 completion」两个方向也都不成立： 已装 APK 的 libapp.so 里能 strings 到修复字面量， 且 _speakCurrent 本来就有 on TTSUnpronounceableFragmentException → _onServiceCompleted()。

  • 修法（客户端）：新增 EdgeTTSService.isSynthesisFailureResponse() 作为这条契约的唯一判定点 —— 422 → 跳过；502 则再嗅 JSON 标记（兼容未升级的旧服务端）； 其余一律仍按真实错误上报（不透明 502 不会被当成可跳过，避免服务真挂时静默读完整本书）。 顺手订正了旧注释里写死的「502」。
