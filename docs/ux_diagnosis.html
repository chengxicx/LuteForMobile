基于源码静态审查 · 目标：定位"用起来别扭"的具体成因，而不是泛泛说"UI 不好看"

1先说结论

你的直觉是对的，但原因不是"配色不好看"或"组件不够花哨"。 真正的问题集中在三件事：导航是桌面布局、状态色在物理上分不开、 词条弹窗把整屏吃掉了。其余是触摸层的细节缺失。

一句话概括：功能都在，但每一个交互都缺了"最后 20%"—— 没有触觉、动画不跟手、颜色分辨不出、选项没有分组。 这 20% 恰好就是"手感"的全部。

为什么这不是"风格选择"问题：抽屉导航在手机上会让 每一次页面切换都打断阅读流——抽屉滑出时阅读区被压暗、内容被遮挡、还要再滑回去。 而阅读类 App 最高频的动作恰恰是"读完这段，去查个词/看下进度"。 把 5 个目的地放到常驻底栏，这个来回就消失了。

3根因二：状态色在物理上分不开

这是我认为最严重的问题。Lute 的核心反馈循环是"这个词我熟不熟"， 全靠颜色编码。但当前的状态色不仅互相接近，而且被 alpha 冲淡后更加难以区分。

而且这不是"配色品味"问题，是数学问题——ΔE < 10 就是分不出， 再怎么调屏幕亮度也救不回来。

成因

状态色是按"从生到熟"的顺序拍的，但选色时只在同一个色相带里调明度， 而且 status1–5 一律加 0x88 / 0x99 的 alpha。 透明度和明度两个变量同时变，导致它们全挤在 Lab 空间的同一个小区域里。 

// theme_presets.dart —— 浅色主题现状
status: const StatusColors(
  status1: Color(0x88b46b7a),   // α53% 玫瑰棕
  status2: Color(0x88BA8050),   // α53% 橙棕  ← 与 3 差 ΔE 8.4
  status3: Color(0x88BD9C7B),   // α53% 浅棕  ← 与 2 差 ΔE 8.4
  status4: Color(0x88756D6B),   // α53% 灰棕
  status5: Color(0x4477706E),   // α27% 灰  ← 几乎看不见
  status98: Color(0xFF756D6B),  // ← 与 status4 同 RGB！
  status99: Color(0xFF419252),  // 唯一跳出色相带的
);
修法方向（不用改架构）：把"明度渐变"换成"色相环分段"—— status1 → status5 沿 暖→冷 走一圈（如 玫红 → 橙 → 黄 → 青 → 蓝）， 每档保持相同明度与饱和度，并取消 alpha（透明度交给专门的"淡出"层级去表达）。 这样任意两档的 ΔE 都能稳定在 25 以上。 具体色值我在第 6 节给了可直接替换的一套。

5触摸层的"最后 20%"

这一节全是细节，但"手感"就是由这些细节堆出来的。每一条都独立、改动量都不大。

① 全 App 没有任何触觉反馈

grep -rn "HapticFeedback" lib → 0 处命中。 翻页没有、点词没有、切换状态没有、长按选词没有。

触觉是手机上"操作被确认了"最廉价也最有效的信号。 缺少它，用户会觉得界面"发飘"、"没咬合感"——这正是"手感差"最典型的体感来源。 加上它只需要一行代码，收益却是全局的。 
// 每个关键动作加一行即可
HapticFeedback.selectionClick();   // 切换状态、滑到整数档
HapticFeedback.lightImpact();      // 翻页、打开词条
HapticFeedback.mediumImpact();     // 长按进入选词模式
HapticFeedback.heavyImpact();      // 操作失败 / 删除

② 翻页不跟手

翻页只挂在 onHorizontalDragEnd 上，判定 velocity > 300 后 播一个固定 300ms 的 _PageTransition。 手指拖动过程中页面纹丝不动，松手才"啪"地跳过去。 真正的翻页手感应该让页面跟着手指走，松手再按速度决定翻还是回弹。

reader_screen.dart:1117-1161（onHorizontalDragEnd）· :52-96（_PageTransition 固定 300ms）

④ 双击会先触发单击

没有用 GestureDetector.onDoubleTap，而是手写计时器： 第一次 tap 立刻调 onTap（弹提示），同时起一个 doubleTapTimeout 计时器；若在窗口内第二次 tap，才取消并改走 onDoubleTap。 所以每次双击都会先闪出一次提示再消失。单击响应倒是即时，代价是双击必脏。

text_display.dart:199-246（_handleTap 手写单/双/三击状态机）

⑤ 长按选词的算法复杂度是 O(n)

每个词都包了 RepaintBoundary + GlobalKey + GestureDetector。 长按拖动选词时，每次指针移动都调 _findItemAtGlobalPosition， 它新建一份全页词条列表，然后逐个 findRenderObject() + localToGlobal 做命中测试： 

// text_display.dart:290-306 —— 每次 onLongPressMoveUpdate 都会跑一遍
TextItem? _findItemAtGlobalPosition(Offset globalPosition) {
  for (final item in _allItems()) {          // ← 每帧重新 expand 出整个列表
    final renderObject = itemKey?.currentContext
        ?.findRenderObject();                  // ← 每项一次树查找
    final rect = renderObject.localToGlobal(Offset.zero)
        & renderObject.size;                    // ← 每项一次矩阵变换
    if (rect.contains(globalPosition)) return item;
  }
}

一页 500 个词，就是每次移动 500 次树查找 + 500 次矩阵变换， 而指针移动事件每秒 60–120 次。这解释了长按选词时的黏滞感。 同时 GlobalKey 本身在 Flutter 里就是有成本的（需要注册到全局 key 表）， 一页几百个属于滥用。

text_display.dart:290-306 · :259-262（GlobalKey 池）· :153-176（每词一个 RepaintBoundary）

⑥ 动画曲线只有两种

全项目只用了 Curves.easeInOut（14 次）和 Curves.easeOut（5 次）， 时长集中在 100–200ms，没有一处用弹簧或 M3 的 emphasized 曲线。 easeInOut 是"匀速感"曲线，用在开关、按钮、状态切换上会显得机械。 这类小控件用带一点过冲的 Curves.easeOutBack 或 SpringSimulation，体感差别非常明显。

全项目 grep：Curves 仅 2 种 · 无 pageTransitionsTheme 自定义

P1没有信息架构，只有一长串

当前顺序是：服务器配置 → 认证/登录 → 测试连接/保存 → 备份恢复 → 服务器信息 → 语言设置 → 阅读行为 → 翻页 → 预加载 → …（还有更多）

改法不必大动干戈：先加"分组标题 + 分隔线"把视觉层级做出来， 再把连接层（服务器配置、认证）整块挪进一个二级页 （它属于"配置一次就不管"的内容，不该占据首屏）。 这两步就能把首屏从"看不懂的一长串"变成"三块能扫读的内容"。
